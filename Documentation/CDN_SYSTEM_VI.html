Hệ thống CDN — Thiết kế, Kế hoạch triển khai & Vận hành

Phân phối nội dung từ xa cho com.game.addressables. Ba tài liệu: xây cái gì, triển khai ra sao, và host — vận hành thế nào.

Đọc cái này trước

Package hiện tại chưa có hệ thống CDN — chỉ có ba wrapper mỏng quanh API download của Addressables, không có đường cập nhật catalog, không có pipeline build content-update, và BuildRemoteCatalog đang tắt trong project settings. Mỗi lần build là một full build, nên người chơi phải tải lại 100% remote content cho mỗi bản patch. Đây là nút thắt quyết định, và cũng là lý do kế hoạch triển khai đặt pipeline build lên trước mọi việc runtime.

Không có BuildContentUpdate thì mỗi build là một full build: toàn bộ hash của bundle đổi hết, nên mỗi người chơi tải lại 100% remote content cho mỗi patch. Đây là nút thắt quyết định. 3. Nguyên tắc thiết kế

  1. Giữ đúng phong cách package hiện tại. API phân tầng (facade Cdn → interface service → Addressables thuần), chữ ký kép #if UNITASK_PRESENT, config bằng ScriptableObject, và cặp Result/Error song song với LoadResult<T> / LoadError sẵn có.
  2. Kết quả tường minh, không dùng giá trị sentinel. Mọi thao tác có thể thất bại đều trả CdnResult<T>. Không method nào trả 0, null hay false để ám chỉ hai chuyện khác nhau.
  3. Mặc định hủy được. Mọi điểm vào async của CDN đều nhận CancellationToken.
  4. Byte, không phải phần trăm. Mọi progress hiển thị cho người dùng đều suy ra từ AsyncOperationHandle.GetDownloadStatus().
  5. Suy giảm, đừng sập. Lỗi mạng lúc boot thì suy giảm xuống dùng content đã cache. Chỉ trường hợp cài mới lần đầu mà vừa không mạng vừa không cache mới là điểm dừng cứng, và trạng thái đó phải được báo tường minh để game hiện màn hình riêng.
  6. Service là interface. ICatalogService, IDownloadService, ICacheService, ICdnTelemetry — để test thay được bằng fake và game thay được bằng implementation riêng.
  7. Không giấu singleton trong tầng service. Facade tĩnh Cdn chỉ là lớp tiện lợi bọc quanh CdnRuntime có thể inject; mọi thứ chạm được qua facade đều khởi tạo trực tiếp được.

5. Đặc tả từng module

5.1 CdnSettings (ScriptableObject)

Một asset duy nhất, nạp qua Resources hoặc một addressable ở địa chỉ cố định để chính nó cũng patch được.

[CreateAssetMenu(menuName = "Addressable Manager/CDN Settings")]
public sealed class CdnSettings : ScriptableObject
{
    public List<CdnEnvironment> Environments;
    public string DefaultEnvironmentId;          // ghi đè được lúc runtime
    public DownloadPolicy DefaultPolicy;
    public bool AutoCheckCatalogOnInitialize;    // mặc định true
    public bool AutoApplyCatalogUpdate;          // mặc định true
    public bool CleanBundleCacheAfterUpdate;     // mặc định true
    public float CatalogRequestTimeoutSeconds;   // mặc định 15
}

[Serializable]
public sealed class CdnEnvironment
{
    public string Id;              // "dev" | "staging" | "prod"
    public string BundleBaseUrl;   // https://cdn.example.com/game/{platform}/bundles
    public string CatalogBaseUrl;  // https://cdn.example.com/game/{platform}/{appVersion}
    public bool RequiresAuthHeader;
}

{platform} và {appVersion} là token được CdnRuntime phân giải lúc runtime, nhờ vậy một asset settings phục vụ được mọi build target.

5.2 DownloadPolicy

[Serializable]
public sealed class DownloadPolicy
{
    public int    MaxRetries            = 3;
    public float  InitialBackoffSeconds = 1f;
    public float  BackoffMultiplier     = 2f;
    public float  MaxBackoffSeconds     = 30f;
    public float  JitterRatio           = 0.2f;   // ±20% để tránh dồn tải cùng lúc
    public int    BundleTimeoutSeconds  = 30;
    public int    MaxConcurrentRequests = 6;
    public bool   RequireUnmeteredNetwork = false; // "chỉ tải qua wifi"
    public long   MinFreeDiskBytes      = 200L * 1024 * 1024;
}

Retry áp cho toàn bộ thao tác download, không áp cho từng bundle — Addressables đã retry từng bundle qua BundleRetryCount rồi. Hai tầng bổ trợ nhau: BundleRetryCount xử lý một lỗi 5xx thoáng qua trên một bundle; RetryPolicy xử lý tình huống "thao tác thất bại, người dùng vừa có wifi lại, thử lại đi".

5.3 ICatalogService

Nắm mọi thứ liên quan tới content catalog.

public interface ICatalogService
{
    UniTask<CdnResult<CdnInitReport>>      InitializeAsync(CancellationToken ct);
    UniTask<CdnResult<CatalogUpdateInfo>>  CheckForUpdateAsync(CancellationToken ct);
    UniTask<CdnResult<CatalogApplyReport>> ApplyUpdateAsync(CatalogUpdateInfo info, CancellationToken ct);
}

Ghi chú triển khai:

  • InitializeAsync bọc Addressables.InitializeAsync() và await tường minh thay vì dựa vào việc khởi tạo ngầm bên trong lệnh load đầu tiên. Nhờ vậy lỗi init quan sát được.
  • CheckForUpdateAsync bọc Addressables.CheckForCatalogUpdates(autoReleaseHandle: false) để handle có thể được kiểm tra và release một cách xác định.
  • ApplyUpdateAsync bọc Addressables.UpdateCatalogs(catalogs, autoReleaseHandle: false, autoCleanBundleCache: settings.CleanBundleCacheAfterUpdate).
  • Hành vi offline: nếu NetworkPolicy báo không có mạng, CheckForUpdateAsync trả CdnResult.Success(CatalogUpdateInfo.None) kèm WasOfflineFallback = true — đây không phải lỗi. Addressables sẽ phân giải catalog đã cache trước đó.
  • Cài mới mà offline: InitializeAsync phát hiện tình trạng "không có catalog cache và không có mạng" và trả CdnErrorCode.NoContentAvailableOffline. Đây là điểm dừng cứng hợp lệ duy nhất.

5.4 IDownloadService

public interface IDownloadService
{
    UniTask<CdnResult<long>>           GetDownloadSizeAsync(DownloadRequest req, CancellationToken ct);
    UniTask<CdnResult<DownloadReport>> DownloadAsync(DownloadRequest req,
                                                     IProgress<DownloadProgress> progress,
                                                     CancellationToken ct);
}

public sealed class DownloadRequest
{
    public IReadOnlyList<object> Keys;          // address, label, hoặc AssetReference
    public Addressables.MergeMode MergeMode = Addressables.MergeMode.Union;
    public DownloadPolicy PolicyOverride;       // null → lấy mặc định từ settings
}

Vòng lặp progress thay cho implementation dựa trên phần trăm hiện tại:

var status = handle.GetDownloadStatus();       // DownloadStatus { DownloadedBytes, TotalBytes, IsDone }
long deltaBytes = status.DownloadedBytes - lastBytes;
float deltaTime = Time.unscaledDeltaTime;      // delta thật của frame, không phải thời gian từ lúc bắt đầu
// làm mượt bằng EMA để con số không nhấp nháy từng frame
speedBytesPerSecond = Mathf.Lerp(speedBytesPerSecond, deltaBytes / deltaTime, 0.1f);
eta = speedBytesPerSecond > 0
    ? (status.TotalBytes - status.DownloadedBytes) / speedBytesPerSecond
    : -1f;                                     // -1 = chưa biết, tuyệt đối không bịa số

Callback progress được tiết chế (mặc định 4 Hz) thay vì bắn mỗi frame. Vì DownloadProgress là struct và callback là IProgress<T>, vòng lặp không sinh rác ở trạng thái ổn định.

Kiểm tra trước khi bắt đầu, mỗi cái ánh xạ về một mã lỗi riêng:

  1. Mạng có kết nối, và không tính phí nếu bật RequireUnmeteredNetwork.
  2. Caching.defaultCache.spaceFree ≥ dung lượng tải + MinFreeDiskBytes.
  3. Truy vấn dung lượng thành công (truy vấn thất bại không được coi là "0 byte cần tải").

{

5.6 CdnRequestDecorator

Hai hook của Addressables, cả hai đều được cài đúng một lần khi dựng CdnRuntime.

Addressables.WebRequestOverride = request =>
{
    request.timeout = policy.BundleTimeoutSeconds;
    if (environment.RequiresAuthHeader)
        request.SetRequestHeader("Authorization", tokenProvider.Current);
    request.SetRequestHeader("X-Client-Version", Application.version);
};

Addressables.InternalIdTransformFunc = location =>
{
    // Đổi host đã ghi trong catalog lúc build sang host chọn lúc runtime.
    // Cho phép: chuyển dev/staging/prod không cần rebuild, và failover CDN.
    return hostRewriter.Rewrite(location.InternalId);
};

InternalIdTransformFunc chính là thứ tách catalog đã build ra khỏi một hostname cụ thể. Catalog được build với một host placeholder; runtime thay bằng host thật. Đây cũng là cơ chế failover: khi host A liên tục lỗi, hostRewriter nâng host B lên và lần retry sẽ phân giải sang origin khác.

Ràng buộc thứ tự

InternalIdTransformFunc phải được cài trước Addressables.InitializeAsync(), nếu không thì chính request lấy catalog cũng không được rewrite. CdnRuntime đảm bảo thứ tự này.

5.7 NetworkPolicy và RetryPolicy

NetworkPolicy bọc Application.internetReachability và expose IsReachable, IsMetered (ReachableViaCarrierDataNetwork), cùng helper WaitForReachableAsync(ct) dùng để nối lại một download đang tạm dừng khi có mạng trở lại.

internetReachability báo về giao diện mạng, không phải khả năng ra internet thật (captive portal vẫn báo là có mạng). Chỉ nên coi nó là phép kiểm tra âm tính nhanh: nếu nó báo không có mạng thì bỏ qua request; nếu nó báo có mạng thì vẫn phải xử lý lỗi bình thường.

RetryPolicy tính min(initial * multiplier^attempt, max) * (1 ± jitter) và quyết định có retry hay không dựa trên bảng mã lỗi ở §8 — 5xx và timeout thì retry, 403/404 và CRC mismatch thì không.

5.8 ICdnTelemetry

Hook kiểu bắn-rồi-quên để game tự chuyển tiếp sang hệ analytics của mình. Package không kèm tầng truyền tải nào.

public interface ICdnTelemetry
{
    void OnCatalogChecked(CatalogUpdateInfo info, TimeSpan duration, CdnError error);
    void OnDownloadCompleted(DownloadReport report);
    void OnDownloadFailed(DownloadRequest req, CdnError error, int attempt);
    void OnCacheCleaned(long bytesFreed);
}

Các chỉ số nên suy ra: tỉ lệ download thành công, thời lượng p50/p95 theo nhóm dung lượng, phân bố mã lỗi, số byte phục vụ theo từng app version. Không có mấy con số này thì không phân biệt được lỗi CDN với lỗi client.

Tầng 2 — service

CdnRuntime.Catalog, .Download, .Cache expose các interface ở §5 cho những caller cần inject policy riêng theo từng lệnh gọi hoặc thay implementation.

Tầng 3 — nâng cao

Constructor của CdnRuntime nhận (CdnSettings, ICatalogService, IDownloadService, ICacheService, ICdnTelemetry), nên game thay được bất kỳ phần nào. CdnRequestDecorator expose IHostRewriter và IAuthTokenProvider cho các phương án signed-URL hoặc refresh token.

Cách dùng chuẩn

async UniTask BootAsync(CancellationToken ct)
{
    var init = await Cdn.InitializeAsync(ct: ct);
    if (!init.IsSuccess)
    {
        if (init.Error.Code == CdnErrorCode.NoContentAvailableOffline)
        { ShowFirstInstallNeedsInternetScreen(); return; }
        // mọi lỗi init khác → chạy tiếp bằng content đã cache
        Log.Warn(init.Error);
    }

    var update = await Cdn.CheckForUpdateAsync(ct);
    if (update.IsSuccess && update.Value.HasUpdate)
    {
        await Cdn.ApplyUpdateAsync(ct);

        var size = await Cdn.GetDownloadSizeAsync("preload_core");
        if (size.IsSuccess && size.Value > 0)
        {
            if (!await ConfirmDownloadAsync(size.Value)) return;

            var progress = new Progress<DownloadProgress>(p =>
                patchUI.Set(p.NormalizedProgress, p.DownloadedBytes, p.TotalBytes,
                            p.BytesPerSecond, p.EstimatedSecondsRemaining));

            var result = await Cdn.DownloadAsync("preload_core", progress, ct);
            if (!result.IsSuccess) ShowPatchFailed(result.Error);
        }
    }

    await Cdn.CleanObsoleteBundlesAsync(ct);
}

Để ý những gì caller làm được mà hôm nay chưa làm được: phân biệt "không có gì để tải" với "truy vấn dung lượng thất bại", hủy được, hiện số byte thật, và rẽ nhánh theo lỗi có kiểu.

7. Luồng boot và download

7.1 Boot nguội, có mạng, cài mới lần đầu
Cài decorator (WebRequestOverride + InternalIdTransformFunc)
  → Addressables.InitializeAsync()          lấy catalog từ CatalogBaseUrl
  → CheckForUpdateAsync()                   chưa có catalog cache → HasUpdate = false
  → GetDownloadSizeAsync(khóa preload)      dung lượng đầy đủ
  → DownloadAsync(...)                      progress chính xác theo byte
  → sẵn sàng
7.2 Boot ấm, có mạng, content không đổi
Initialize → CheckForUpdate → hash catalog khớp → HasUpdate = false → sẵn sàng

Chi phí: một request lấy file .hash (vài byte). Đây là lý do file .hash phải có TTL ngắn ở edge — xem hạ tầng §3.

7.3 Boot ấm, có mạng, content đã đổi
Initialize → CheckForUpdate → HasUpdate = true, catalogs = [id]
  → ApplyUpdateAsync (UpdateCatalogs, autoCleanBundleCache = true)
  → GetDownloadSizeAsync → chỉ phần delta, vì các bundle không đổi vẫn nằm trong cache và
                            hash của chúng không đổi (đây chính là điều BuildContentUpdate đảm bảo)
  → DownloadAsync → sẵn sàng
7.4 Boot ấm, không mạng
Initialize → NetworkPolicy.IsReachable == false
  → Addressables phân giải catalog đã cache
  → CheckForUpdate đoản mạch: Success(None, WasOfflineFallback = true)
  → bỏ qua GetDownloadSize
  → sẵn sàng, chạy bằng content đã cache

Không exception, không hộp thoại chặn. Game có thể hiện một chỉ báo "offline" thụ động.

7.5 Boot nguội, không mạng, cài mới lần đầu
Initialize → không có catalog cache + không có mạng
  → CdnResult.Failure(NoContentAvailableOffline)
  → game hiện màn hình riêng "kết nối internet để hoàn tất cài đặt"
7.6 Download có retry
lần 0 → 503 trên bundle X
  → RetryPolicy.ShouldRetry(ServerError) = true, chờ 1s ± 20%
lần 1 → mất kết nối giữa chừng
  → phần byte đã tải vẫn nằm trong cache của Unity; Addressables tiếp tục từ phần đã có
  → chờ 2s ± 20%
lần 2 → thành công
  → DownloadReport { BytesDownloaded, Duration, Attempts = 3, ResumedFromPartial = true }
7.7 Hủy giữa chừng

Khi ct bị hủy, vòng await dừng và handle được release. Số byte đã ghi vào cache của Unity được giữ lại — lần download sau tiếp tục chứ không tải lại từ đầu. Kết quả trả về là CdnResult.Cancelled, khác với thất bại, nên UI không hiện toast lỗi khi người dùng chủ động bấm Back.

7.8 Đầy ổ đĩa giữa chừng

Bước kiểm tra trước bắt được trường hợp phổ biến. Nếu máy đầy trong lúc đang truyền, Addressables sẽ báo lỗi caching; DownloadService ánh xạ nó sang CdnErrorCode.InsufficientDiskSpace và báo RequiredBytes / AvailableBytes để UI nói được cần giải phóng bao nhiêu.

13. Câu hỏi còn mở

  1. Phiên bản Addressables. Package đang ghim com.unity.addressables: 2.3.1; bản hiện tại là 2.9.x. Nâng cấp trước khi viết code này thì tránh phải làm lại, nhưng cần một lượt kiểm tra hồi quy trên các loader hiện có. Khuyến nghị: nâng ở Phase 0.
  2. CdnSettings đặt ở đâu? Resources (luôn có trong build, đơn giản) hay một addressable local (patch được, nhưng vướng bài toán con gà quả trứng với khâu khởi tạo). Khuyến nghị: Resources, và cho phép ghi đè môi trường bằng tham số runtime để QA trỏ build prod sang staging được.
  3. Signed URL hay token header? Signed URL đồng nghĩa catalog không chứa được URL cuối, buộc mọi thứ phải rewrite qua InternalIdTransformFunc kèm bước ký cho từng request. Bearer header qua WebRequestOverride đơn giản hơn nhiều. Khuyến nghị: dùng header, trừ khi có yêu cầu cứng phải chặn chia sẻ link.
  4. Có cần ưu tiên tải theo từng bundle không? Addressables không expose độ ưu tiên hàng đợi cho việc tải dependency. Chỉ đạt được bằng cách tách thành nhiều lệnh DownloadAsync tuần tự theo label. Khuyến nghị: mô hình hóa độ ưu tiên bằng các nhóm label có thứ tự, không xây scheduler.
  5. ProgressInfo hay DownloadProgress? Có hai kiểu progress là một vết gợn. Gộp lại thì đổi ngữ nghĩa ProgressInfo với caller hiện tại. Khuyến nghị: giữ cả hai suốt 4.x, có adapter giữa chúng, gộp ở 5.0.0.

1. Chiến lược

Lý do chọn thứ tự này

Bản năng là bắt tay vào code runtime trước, vì đó là nơi có API nhìn thấy được. Ở đây thì đó là thứ tự sai.

Hôm nay mỗi build là một full build. Hash bundle đổi hàng loạt, nên người chơi tải 100% remote content cho mỗi patch. Chừng nào BuildContentUpdate chưa được nối vào, một download service dựng công phu cỡ nào cũng chỉ đang tải toàn bộ mọi thứ — nhanh và có thanh progress đẹp. Pipeline là nút thắt, nên nó đi đầu.

Lý do thứ hai: pipeline sinh ra các artifact (catalog thật, bundle thật, một file addressables_content_state.bin thật) mà Phase 2–4 cần để test bằng thứ gì đó ngoài mock. Xây nó trước nghĩa là mọi phase sau đều kiểm chứng được đầu-cuối ngay từ ngày đầu.

Nguyên tắc xuyên suốt

  1. Mỗi phase đều giao được thứ dùng được. Không phase nào để lại nhánh ở trạng thái tệ hơn main.
  2. Không làm vỡ gì trên main. API hiện có vẫn chạy suốt cả kế hoạch; đánh dấu deprecated ở 4.1.0 và không gỡ trước 5.0.0.
  3. Hạ tầng và code tiến cùng nhau. Một tính năng runtime không có content đã deploy để test thì chưa gọi là xong.
  4. Mỗi phase có tiêu chí thoát kiểm chứng được. "Nó chạy được" không phải tiêu chí thoát; "thay đổi content 2 MB tạo ra patch ≤ 2.5 MB, đã kiểm trên máy thật" mới là.

Cơ sở ước lượng

Công sức tính bằng ngày-người lý tưởng cho một dev đã quen Addressables, chưa tính thời gian chờ review và chờ cấp phát hạ tầng. Bạn tự nhân thêm hệ số của mình.

11. Quy trình rollback

Deploy nhầm content xấu. Upload lại catalog trước đó cho app version bị ảnh hưởng. Vì bundle được đánh địa chỉ theo nội dung và chỉ thêm chứ không sửa, bundle cũ vẫn còn nguyên — chỉ cần đổi catalog là rollback trọn vẹn. Thời gian phục hồi bằng một lần upload cộng TTL của .hash (≤ 60 giây).

Player build lỗi. Không rollback được qua CDN; phải phát hành lại lên store. Đây chính là lý do thay đổi content static phải bị bắt ngay lúc build (R5).

Package sai phiên bản trong một project game. Mỗi phase là một minor version độc lập; chỉ cần revert dependency UPM. Vì API cũ còn giữ tới 5.0.0, hạ từ 4.x xuống 4.x là an toàn.

Cache client hỏng ngoài thực địa. Cdn.ClearCacheAsync(key) để xử lý có mục tiêu, hoặc ClearAllAsync làm phương án cuối. Nên đặt sau một cờ remote-config để kích hoạt được mà không cần cập nhật client.

12. Định nghĩa hoàn thành

Hệ thống CDN được coi là xong khi tất cả những điều sau đều đúng:

  1. Một thay đổi chỉ về content đến được tay người chơi qua CI, không cần bước thủ công nào trong Editor.
  2. Người chơi chỉ nhận phần delta; kích thước patch đo được nằm trong khoảng 25% so với kích thước asset đã đổi.
  3. Game boot offline được với cache ấm, không hộp thoại lỗi.
  4. Mọi kiểu lỗi trong bảng ở thiết kế §8 đều chạm tới được trong test và có trong tài liệu khắc phục sự cố.
  5. Download hủy được và tiếp tục được từ phần đã tải.
  6. Progress báo byte thật; tốc độ và ETA nằm trong ±15% khi bị bóp băng thông.
  7. Dung lượng đĩa không phình lên qua các lần content update liên tiếp.
  8. Rollback một bản deploy content xấu mất một lần upload và dưới một phút.
  9. Telemetry trả lời được câu "tuần này tỉ lệ download thành công là bao nhiêu, và lỗi tập trung ở đâu".

Addressables không quan tâm ai phục vụ nội dung — nó chỉ cần một URL trả về catalog, file hash của catalog, và các bundle. Nhờ vậy việc chọn origin là tự do, và R2 đứng sau CDN của Cloudflare là phương án tiết kiệm: R2 không tính phí egress ra internet, còn bundle đã cache thì được phục vụ từ biên.

Unity Cloud Content Delivery vẫn là lựa chọn thay thế cắm-là-chạy (đổi một biến profile) nếu tính tiền theo băng thông về sau lại có lợi hơn việc tự vận hành. Không có gì trong thiết kế bị trói vào R2.

2. Bố cục lưu trữ

Quyết định then chốt

Đây là quyết định hệ trọng nhất trong tài liệu này. Sai chỗ này thì hoặc patch vỡ, hoặc cache vỡ.

Vì sao tách bundle khỏi catalog

Addressables cho phép cấu hình đường dẫn remote catalog độc lập với load path của group (RemoteCatalogBuildPath / RemoteCatalogLoadPath trong settings, so với LoadPath trên schema của group). Tận dụng sự tách bạch đó ta có hai loại object với vòng đời trái ngược nhau:

  • Bundle là bất biến và dùng chung. Tên file bundle chứa hash nội dung, nên một asset thay đổi sẽ sinh ra file mới chứ không ghi đè file cũ. Player cũ vẫn phân giải được bundle cũ; player mới lấy bundle mới. Thư mục chỉ thêm chứ không sửa, và mọi object đều cache được cả năm.
  • Catalog thay đổi được và gắn với từng app version. Một bản content update ghi đè catalog của đúng một app version. Nó không được cache lâu, và không bao giờ được dùng chung giữa các app version — một catalog do BuildContentUpdate sinh ra chỉ hợp lệ với content_state.bin của đúng player build đã sinh ra nó.

Gộp cả hai vào một thư mục thì buộc phải áp cùng một chính sách cache, tức là hoặc catalog bị cũ, hoặc bundle bị revalidate ở mỗi request.

Cấu hình group bắt buộc

Tên bundle bắt buộc phải chứa hash nội dung — chọn Append Hash to Filename hoặc Use Hash of AssetBundle trên BundledAssetGroupSchema của group. Không có hash trong tên file thì một bản content update sẽ ghi đè lên các object bundle đang tồn tại, đồng thời phá vỡ cache bất biến và phá vỡ mọi player còn ở content version trước. CatalogVerifier kiểm tra điều này.

Lúc runtime, phần host được InternalIdTransformFunc rewrite (thiết kế §5.6), nên các URL nướng sẵn này đóng vai trò dự phòng chứ không phải lựa chọn duy nhất.

Purge khi deploy

TTL là lưới an toàn, không phải cơ chế lan truyền. Mỗi lần deploy đều purge prefix catalog một cách tường minh:

curl -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/purge_cache" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  --data "{\"files\":[
      \"https://cdn.$DOMAIN/$GAME/$PLATFORM/catalog/$APP_VERSION/catalog_$APP_VERSION.hash\",
      \"https://cdn.$DOMAIN/$GAME/$PLATFORM/catalog/$APP_VERSION/catalog_$APP_VERSION.bin\"
  ]}"

Purge cả hai cùng lúc để tránh khoảng thời gian client thấy .hash mới nhưng catalog thì cũ. Tuyệt đối không purge prefix bundle — những object đó bất biến, purge chỉ khiến biên phải tải lại đúng những byte y hệt từ origin.

5. Quy trình deploy

Thứ tự là quan trọng. Mỗi bước là cổng chặn cho bước sau.

1. Build          BuildContent (full) hoặc BuildContentUpdate (delta)
                  └─ cần: đúng profile, có content_state.bin nếu là bản update
2. Verify         CatalogVerifier — ràng buộc cấu hình, tính nhất quán catalog↔bundle
                  └─ làm fail job trước khi có bất cứ thứ gì ra tới mạng
3. Upload bundle  bundles/ → R2, Cache-Control: immutable
                  └─ chỉ thêm; không bao giờ ghi đè object đã có
4. Upload catalog catalog/<appVersion>/ → R2, Cache-Control: must-revalidate
                  └─ LUÔN LUÔN SAU BUNDLE
5. Purge          .hash và thân catalog ở biên
6. Kiểm tra sau   HEAD mọi URL trong manifest; kiểm 200 và header đúng như mong đợi
7. Lưu trữ        content_state.bin + build-manifest.json → kho artifact của CI
Vì sao thứ tự quan trọng

Bước 3 trước bước 4 không phải là sở thích hình thức. Upload catalog trước tạo ra một khoảng thời gian mà client đọc được catalog trỏ tới những bundle chưa tồn tại, sinh ra 404 trên môi trường production. Bundle-rồi-catalog khiến bản deploy trở nên nguyên tử dưới góc nhìn của client: nội dung mới vô hình cho tới khi catalog gọi tên nó.

Lệnh upload

R2 tương thích S3.

# 3. bundle — bất biến, chỉ thêm
aws s3 sync "ServerData/$PLATFORM/bundles/" "s3://$BUCKET/$GAME/$PLATFORM/bundles/" \
  --endpoint-url "$R2_ENDPOINT" \
  --cache-control "public, max-age=31536000, immutable" \
  --content-type "application/octet-stream" \
  --size-only

# 4. catalog — TTL ngắn, ghi đè
aws s3 sync "ServerData/$PLATFORM/catalog/$APP_VERSION/" \
  "s3://$BUCKET/$GAME/$PLATFORM/catalog/$APP_VERSION/" \
  --endpoint-url "$R2_ENDPOINT" \
  --cache-control "public, max-age=0, must-revalidate" \
  --exclude "build-manifest.json"

Dùng --size-only cho bước đồng bộ bundle là an toàn, chính bởi vì tên file đã băm theo nội dung: trùng tên nghĩa là trùng byte.

Kiểm tra sau deploy

# mọi URL trong manifest phải trả 200 với header cache đúng
jq -r '.bundles[].url, .catalog.url, .catalog.hashUrl' build-manifest.json \
  | while read -r url; do
      code=$(curl -sS -o /dev/null -w '%{http_code}' -I "$url")
      [ "$code" = "200" ] || { echo "FAIL $code $url"; exit 1; }
    done

Một bản deploy bỏ qua bước này chính là con đường để rủi ro R2 (sổ rủi ro) đi thẳng vào production.

6. Vòng đời content state

addressables_content_state.bin ghi lại trạng thái content tại thời điểm một player build được tạo ra. BuildContentUpdate so sánh với nó để quyết định bundle nào cần build lại.

Nghiêm trọng

Mất nó với một app version đã ship là chấm dứt vĩnh viễn khả năng delta update cho version đó. Mọi bản patch sau này cho những người chơi đó đều biến thành tải lại toàn bộ. Không có cách nào dựng lại file này.

Quy tắc

  1. Lưu ngoài Assets/ — ServerData/ContentState/[BuildTarget]/ — và cho vào gitignore. Để trong Assets/ thì nó thay đổi ở mọi commit và bị resolve sai khi merge.
  2. Lưu trữ dưới dạng artifact CI ở mọi build, đánh khóa theo <platform>/<appVersion>/. Đồng thời nhân bản sang một prefix bucket để nó sống lâu hơn thời hạn giữ artifact của CI.
  3. Giữ chừng nào app version đó còn lượng người chơi đáng kể, cộng thêm biên an toàn. Tối thiểu: hai năm hoặc hai major version, lấy cái nào dài hơn.
  4. Một bản build content-update phải fail nếu thiếu file state. Tuyệt đối không được âm thầm tụt về full build — làm vậy sinh ra một catalog trông hợp lệ nhưng ép mọi người chơi tải lại tất cả.
  5. Kiểm tra file state đã lưu trữ khớp với app version đang được patch trước khi dùng.

Lấy về

aws s3 cp "s3://$STATE_BUCKET/$GAME/$PLATFORM/$APP_VERSION/addressables_content_state.bin" \
  "ServerData/ContentState/$PLATFORM/" --endpoint-url "$R2_ENDPOINT"

7. Tham chiếu CI/CD

Hai workflow. Ranh giới giữa chúng đúng bằng ranh giới giữa một bản phát hành player và một bản patch content.

content-full.yml — chạy kèm một player build

name: Content Full Build
on:
  workflow_dispatch:
    inputs:
      platform:    { required: true, type: choice, options: [Android, iOS] }
      environment: { required: true, type: choice, options: [dev, staging, prod] }

jobs:
  build:
    runs-on: [self-hosted, unity]
    steps:
      - uses: actions/checkout@v4

      - name: Build addressable content
        run: |
          "$UNITY" -batchmode -quit -nographics \
            -projectPath . \
            -logFile - \
            -executeMethod AddressableManager.Editor.Cdn.CdnBuildCLI.BuildContent \
            -cdnProfile "${{ inputs.environment }}" \
            -buildTarget "${{ inputs.platform }}" \
            -outputDir "ServerData"

      - name: Verify catalog
        run: |
          "$UNITY" -batchmode -quit -nographics -projectPath . -logFile - \
            -executeMethod AddressableManager.Editor.Cdn.CatalogVerifier.VerifyCli \
            -manifest "ServerData/build-manifest.json"

      - name: Upload bundles
        run: ./ci/upload-bundles.sh
        env: { R2_ENDPOINT: "${{ secrets.R2_ENDPOINT }}" }

      - name: Upload catalog
        run: ./ci/upload-catalog.sh

      - name: Purge edge cache
        run: ./ci/purge-catalog.sh

      - name: Post-deploy check
        run: ./ci/verify-urls.sh

      - name: Archive content state          # không bao giờ được bỏ; xem §6
        uses: actions/upload-artifact@v4
        with:
          name: content-state-${{ inputs.platform }}-${{ env.APP_VERSION }}
          path: ServerData/ContentState/**/addressables_content_state.bin
          retention-days: 90
          if-no-files-found: error

      - name: Mirror content state to durable storage
        run: ./ci/archive-content-state.sh

content-update.yml — patch chỉ content, không build player

Giống hệt, chỉ khác hai bước ở đầu:

      - name: Fetch content state for target app version
        run: ./ci/fetch-content-state.sh
        env:
          APP_VERSION: ${{ inputs.app_version }}

      - name: Build content update
        run: |
          "$UNITY" -batchmode -quit -nographics -projectPath . -logFile - \
            -executeMethod AddressableManager.Editor.Cdn.CdnBuildCLI.BuildContentUpdate \
            -cdnProfile "${{ inputs.environment }}" \
            -buildTarget "${{ inputs.platform }}" \
            -contentState "ServerData/ContentState/${{ inputs.platform }}/addressables_content_state.bin"

BuildContentUpdate đồng thời chạy bước kiểm tra ràng buộc content static (kế hoạch §1.4) và fail nếu một group đánh dấu static bị đổi — tình huống đó không patch được và cần một player build mới.

8. Rollback

Content xấu

Vì bundle chỉ thêm và đánh địa chỉ theo nội dung, content trước đó vẫn còn trên origin. Rollback chỉ là đổi catalog:

# khôi phục catalog trước đó cho app version này
aws s3 cp "s3://$ARCHIVE/$GAME/$PLATFORM/$APP_VERSION/<build-id-truoc>/" \
  "s3://$BUCKET/$GAME/$PLATFORM/catalog/$APP_VERSION/" \
  --recursive --endpoint-url "$R2_ENDPOINT" \
  --cache-control "public, max-age=0, must-revalidate"

./ci/purge-catalog.sh

Thời gian phục hồi: một lần upload cộng 60 giây TTL ở biên. Đây là lý do mỗi lần upload catalog đều phải lưu trữ kèm một build id — không có bản lưu trữ đó thì chẳng có gì để mà rollback về.

Player build lỗi

Không phục hồi được qua CDN. Phải phát hành lại lên store. Đây chính là lý do bước kiểm tra content static là một cổng chặn lúc build chứ không phải một cảnh báo.

Cache hỏng phía client, ngoài thực địa

Cdn.ClearCacheAsync(key) để xóa có mục tiêu, ClearAllAsync là phương án cuối. Cả hai nên đặt sau một cờ remote-config để kích hoạt được mà không phải ship bản client mới.

9. Bảo mật

Mô hình mối đe dọa

Asset bundle không phải bí mật — ai cài game cũng trích xuất được. Xác thực ở CDN là để chống ăn cắp băng thông và lạm dụng, không phải để giữ bí mật.

11. Mô hình chi phí

Các biến số đáng quan tâm, xếp theo mức ảnh hưởng:

  1. Egress. Khoản chi phối với content game ở quy mô lớn, và là lý do chọn R2: object storage không tính phí egress theo GB ra internet, phía trước là một CDN phục vụ cache hit mà không chạm tới origin.
  2. Lưu trữ. Thư mục bundle chỉ-thêm nên phình đơn điệu. Cần dự trù mức tăng và định ra chính sách dọn dẹp cho những app version không còn người chơi (xem phần lưu giữ ở §6).
  3. Thao tác Class A/B. Số lần ghi và đọc trên bucket. Không đáng kể so với egress trừ khi tỉ lệ cache hit kém — mà điều đó lại quay về việc §3 có được cấu hình đúng hay không.
  4. Lãng phí do tải lại toàn bộ. Khoản chi phí tránh được lớn nhất là việc ship full content ở mỗi patch. Đó chính là thứ Phase 1 của kế hoạch triển khai loại bỏ, và nó lớn hơn hẳn mọi việc tinh chỉnh hạ tầng.

Hãy kiểm tra bảng giá hiện hành của nhà cung cấp trước khi lập mô hình; thứ tự định tính ở trên thì ổn định, còn con số thì không. Unity CCD tính tiền theo băng thông và đáng để định giá lại vào thời điểm sự đơn giản trong vận hành có giá trị hơn chi phí egress.

12. Runbook

Người chơi báo "kẹt ở content cũ"

  1. curl -I vào URL của .hash. Xem cf-cache-status và age.
  2. Nếu age lớn thì bước purge đã thất bại hoặc cache rule cấu hình sai → purge thủ công, rồi sửa rule.
  3. Nếu header đúng thì so hash đang được phục vụ với build-manifest.json đã lưu trữ. Lệch nhau nghĩa là đã upload nhầm catalog.

Tăng vọt BundleNotFound

Gần như luôn là do thứ tự upload (§5, bước 3 trước 4) hoặc một lần sync bundle chỉ xong một phần.

  1. So danh sách bundle trong manifest với danh sách object trên bucket.
  2. Upload lại những bundle còn thiếu. Không cần purge — chúng chưa từng được cache.
  3. Kiểm lại cách script deploy xử lý lỗi; một lệnh aws s3 sync chạy dở phải làm fail job.

Tăng vọt BundleCrcMismatch

  1. Xác nhận đây không phải cache hỏng của một client đơn lẻ (kiểm mức độ lan rộng trên nhiều máy).
  2. Nếu diện rộng thì object ở origin đã hỏng — upload lại từ artifact của CI rồi purge.
  3. Đường tự sửa phía client (thiết kế §8) sẽ loại bỏ và thử lại một lần, nên trường hợp thoáng qua tự lành.

Egress bất thường

  1. Kiểm tỉ lệ cache hit trước — một lỗi cấu hình hồi quy ở cache rule của bundle trông y hệt như bị lạm dụng.
  2. Kiểm phân bố request theo IP/ASN xem có bị cào không.
  3. Siết rate limit của WAF; cân nhắc bật hotlink protection nếu chưa bật.

Content update lại sinh ra patch to bằng bản đầy đủ

  1. content_state.bin có mặt và đúng với app version đó không? (§6)
  2. Có group static nào bị đổi không? Xem báo cáo ràng buộc từ bản build.
  3. MonoScriptBundleNaming hoặc BuiltInBundleNaming có đổi giữa hai bản build không? Cả hai đều gây thay đổi bundle trên diện rộng. Cả hai đều bị ghim bởi ràng buộc cấu hình (thiết kế §9) chính vì lý do này.

Cần trỏ một bản build prod sang staging

Dùng cơ chế đổi môi trường lúc runtime (thiết kế §5.6). Xác nhận nó bị khóa cho development build hoặc một lệnh debug có ký — nếu một giá trị config trơn cũng làm được, thì đó là lỗi cần sửa chứ không phải quy trình để dùng.
